# Конфигурация all-in-one

`docker-compose.yml` в этой директории поднимает всё сразу: Postgres, nginx, Redis и
контейнер библиотеки. Ничего внешнего не требуется — это самый короткий путь от
свежего клона репозитория до работающей библиотеки.

Альтернатива — [external_services](../external_services_config/README.md): там
запускается только контейнер библиотеки, а Postgres и веб-сервер (reverse proxy с
HTTPS) у Вас уже есть. Это предпочтительный вариант, если Вы публикуете библиотеку
в интернет сами.

## Главный вопрос: HTTPS

nginx в этой конфигурации слушает обычный HTTP на порту 27100. Само по себе это не
приговор: важно не то, по какому протоколу говорят контейнеры между собой, а то,
что видит браузер читателя. Отсюда три ситуации.

### 1. HTTPS до самого браузера — предпочтительно

Reverse proxy с сертификатом (SWAG, Nginx Proxy Manager, Caddy, Traefik) принимает
HTTPS и сам работает с php-fpm. Для этого используйте
[external_services](../external_services_config/README.md): там не поднимается
лишний nginx и не публикуется лишний порт.

### 2. TLS завершается у третьей стороны — допустимо

Типичный случай — **Cloudflare Tunnel**: `cloudflared` держит исходящее соединение
к Cloudflare, сертификат выдаёт и обслуживает Cloudflare, а до Вашего nginx трафик
доходит уже расшифрованным по HTTP. Белый IP не нужен, порты наружу открывать не
нужно. То же относится к любому другому проксирующему сервису, который завершает
TLS у себя.

В этой схеме all-in-one — вполне рабочий выбор. Два важных момента:

- **`FLIBUSTA_ALLOW_ADMIN_ACCESS_BY_HTTP` оставьте выключенной.** Браузер читателя
  работает по `https://`, поэтому он нормально возвращает cookie с атрибутом
  `Secure` — несмотря на то, что контейнер библиотеки видит только HTTP. Флаг этот
  атрибут снимает, то есть ослабляет защиту без всякой необходимости.
- **Адрес клиента.** Библиотека увидит в `REMOTE_ADDR` адрес туннеля, а не читателя.
  Если Вы пользуетесь `FLIBUSTA_TRUSTED_NET` или fail2ban, пробросьте реальный адрес
  в nginx (для Cloudflare это заголовок `CF-Connecting-IP`, директивы `real_ip_header`
  и `set_real_ip_from`), иначе доверенная сеть и баны будут работать не так, как Вы
  ожидаете.

Заголовок `X-Forwarded-Proto`, если прокси его присылает, `phpdocker/nginx/nginx.conf`
передаёт приложению как есть. Благодаря этому предупреждение «соединение не
защищено» в разделе «Пользователи» не появляется там, где соединение читателя на
самом деле защищено.

### 3. HTTP до браузера — только для изолированных сетей и разработки

Доступ вида `http://адрес-наса:27100/` из домашней сети или локальная разработка,
где сертификат получить попросту нечем (сервер не виден из интернета, значит и
Let's Encrypt его не подтвердит). Здесь придётся включить

```yaml
- FLIBUSTA_ALLOW_ADMIN_ACCESS_BY_HTTP=true
```

иначе cookie сессии уйдёт с атрибутом `Secure`, браузер на `http://` её не вернёт, и
вход будет бесконечно возвращать на форму входа.

**Никогда не используйте этот вариант для библиотеки, доступной из интернета по
`http://`**: пароли, cookie и содержимое книг пойдут по сети открытым текстом.

## Запуск

Все относительные пути в файле (`./cache`, `./Flibusta.Net`, `./secrets`,
`./phpdocker`) рассчитаны на корень репозитория, и образ библиотеки собирается из
самого репозитория. Compose же по умолчанию считает относительные пути от директории
compose-файла, поэтому директорию проекта нужно указать явно:

```bash
cd <корень репозитория>
mkdir -p cache Flibusta.Net FlibustaSQL secrets
# пароли: по одной строке в файле, без перевода строки в конце
docker compose -f docs_and_configs/all_in_one_config/docker-compose.yml \
       --project-directory . up -d
```

Либо скопируйте файл в корень репозитория и запускайте обычным `docker compose up -d`.

Что нужно подготовить:

| Путь | Что это |
|---|---|
| `./Flibusta.Net` | zip-архивы Флибусты (монтируется в контейнер только для чтения) |
| `./FlibustaSQL` | сюда скачиваются дампы БД |
| `./cache` | рабочая директория библиотеки: обложки, логи, временные файлы |
| `./secrets/postgres_admin_pwd.txt` | пароль администратора Postgres |
| `./secrets/flibusta_pwd.txt` | пароль пользователя БД `flibusta` |
| `./secrets/flibusta_app_admin_pwd.txt` | пароль администратора библиотеки |

Дальше — `http://localhost:27100/`, вход администратором из
`FLIBUSTA_APP_ADMIN`, раздел «Сервис», скачивание и импорт базы. Подробности первого
наполнения — в [основном README](../../README.md).

## Статика отдаётся из тома, а не из директории с кодом

Контейнер библиотеки при старте выкладывает содержимое `application/public`
(JS-читалки, CSS, картинки) в именованный том `flibusta_public_files`, а nginx
монтирует этот том **только для чтения**:

```yaml
- flibusta_public_files:/application/public:ro
```

Веб-серверу не нужно ничего записывать в то, что он отдаёт, поэтому уязвимость в
nginx не даёт возможности подменить PHP- или JS-файлы приложения. Больше ничего из
библиотеки в контейнер nginx не монтируется: ни архивы книг, ни `/cache` — они
нужны только php-fpm, а nginx их и не раздаёт.

Из этого следует одно практическое замечание: **правки в `application/` попадают в
работу только после пересборки образа** (`docker compose ... up -d --build`), потому
что код берётся из образа, а не из рабочей копии. Если Вы правите код постоянно,
используйте локальное окружение разработки в [dev/](../../dev/README.md) — там
`application/` смонтирована в контейнер напрямую.

## Отличия от external_services

| | all-in-one | external_services |
|---|---|---|
| Postgres | поднимается здесь | Ваш существующий |
| Веб-сервер | nginx в этом файле, HTTP на 27100 | Ваш reverse proxy с HTTPS |
| Redis | поднимается здесь, включён | необязателен, по умолчанию выключен |
| Образ библиотеки | собирается из репозитория | `blitvin/flibusta-at-home` с Docker Hub |
| fail2ban, logrotate | настраиваете сами | есть готовые конфиги |

Переменные окружения, секреты и тома одинаковы для обеих конфигураций и описаны в
[README external_services](../external_services_config/README.md).
